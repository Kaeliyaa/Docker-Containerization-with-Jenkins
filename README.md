# Docker Containerization with Jenkins

In this project, I learned and tried to explore on how source code can move from GitHub to a deployed Docker container through a Jenkins on a simple CI/CD workflow.

This project inspired by **NotHarshhaa's DevOps Project-05: "Deploy your code on a Docker Container using Jenkins on AWS"** as a learning reference. 

Because the software versions and project setup were different from those used in the original guide, several steps did not work exactly as described. This required me to investigate the errors, understand the underlying process, and find alternative solutions where necessary.

## Project Overview

The goal of this project is to build a simple Java web application and automate its deployment using:

* **GitHub** – source code management
* **GitHub Pull Requests** – controlled code changes
* **GitHub Webhooks** – notify Jenkins about repository changes
* **Jenkins** – CI/CD automation
* **Maven** – building, testing, and packaging
* **SSH / Publish Over SSH** – transferring build artifacts
* **Docker** – containerization and deployment
* **Apache Tomcat** – application server inside the container
* **AWS EC2** – hosting Jenkins and Docker

The resulting workflow is:

```text
Developer
   │
   │ Push / Pull Request
   ▼
GitHub
   │
   │ Webhook
   ▼
Jenkins
   │
   ├── Checkout source code
   │
   ├── Maven build
   │     ├── Compile server
   │     ├── Run tests
   │     └── Package webapp.war
   │
   ├── Transfer WAR through SSH
   ▼
Docker Host
   │
   ├── Build Docker image
   │
   └── Run Docker container
   ▼
Tomcat
   │
   ▼
Deployed Web Application
```

## Understanding the Maven Build

One of the most useful parts of this project was learning how Maven actually processes the repository rather than thinking of it as simply "running a build."

Jenkins runs:

```bash
mvn -f hello-world/pom.xml clean package
```

The `-f` option tells Maven which POM file to use.

Maven then discovers the modules declared by the root project:

```text
Maven Project
    │
    ├── Server
    │     └── server.jar
    │
    └── Webapp
          └── webapp.war
```

The server module produces:

```text
hello-world/server/target/server.jar
```

The web application produces:

```text
hello-world/webapp/target/webapp.war
```

The `target/` directories are generated by Maven during the build process. They contain compiled classes, test reports, packaged artifacts, and other generated build output.

For this deployment, the important artifact is:

```text
hello-world/webapp/target/webapp.war
```

The WAR is then transferred to the Docker host and used as part of the Docker image build.

## Jenkins CI/CD Workflow

The Jenkins job used in this project is:

```text
BuildandDeployonContainer
```

The job performs the following steps.

### 1. Checkout

Jenkins pulls the source code from GitHub into its workspace.

The workspace has a structure similar to:

```text
/var/lib/jenkins/workspace/BuildandDeployonContainer/
└── hello-world/
    ├── pom.xml
    ├── server/
    ├── webapp/
    └── Dockerfile
```

### 2. Build and Test

Maven runs:

```bash
mvn -f hello-world/pom.xml clean package
```

The server module is compiled and tested, while the web application is packaged as a WAR file.

### 3. Transfer the Artifact

The generated WAR is transferred from the Jenkins workspace to the Docker host using Publish Over SSH.

Because my repository structure differs from the original tutorial, the artifact path also had to be changed.

The original tutorial uses:

```text
webapp/target/*.war
```

while my repository requires:

```text
hello-world/webapp/target/*.war
```

This difference caused one of the first deployment issues I encountered.

### 4. Build the Docker Image

On the Docker host, Jenkins executes:

```bash
cd /opt/docker
docker build -t regapp:v1 .
```

### 5. Run the Docker Container

The application is then started with:

```bash
docker run -d --name registerapp -p 8087:8080 regapp:v1
```

The port mapping means:

```text
EC2 host :8087
      ↓
container :8080
      ↓
Tomcat
```

## GitHub Webhook Integration

One improvement I added while adapting the tutorial was **GitHub Webhook integration**.

The original tutorial demonstrates the Jenkins build being triggered after changes are committed to GitHub. For my implementation, I configured a GitHub webhook so that GitHub can notify Jenkins when changes are pushed.

The resulting flow is:

```text
Git push
   ↓
GitHub
   ↓
Webhook
   ↓
Jenkins
   ↓
Build and deployment
```

This allowed me to test the pipeline as an automated workflow rather than manually starting every Jenkins build.

## Adapting the Tutorial to a Different Environment

A major part of this project was dealing with differences between the environment used in the original tutorial and my own setup.

The tutorial was written around a particular set of software versions, configuration paths, and project assumptions. My environment used different versions and configurations, so several instructions could not simply be followed as written.

Instead of changing everything back to match the tutorial, I tried to understand why the original step worked and then adapt it to my environment.

This resulted in several workarounds and alternative solutions.

### Example: Maven could not find the POM

My first Jenkins build failed because Maven could not find a `pom.xml` at the workspace root.

The repository actually contained:

```text
hello-world/pom.xml
```

rather than:

```text
pom.xml
```

The solution was to explicitly tell Maven which POM to use:

```bash
mvn -f hello-world/pom.xml clean package
```

This helped me understand the relationship between the Jenkins workspace, repository structure, and Maven project configuration.
